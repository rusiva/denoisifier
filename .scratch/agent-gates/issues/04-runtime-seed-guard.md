# 04: Runtime seed guard

**What to build:** No test can judge the detector on a frame generated from a calibration seed, however the seed got there. Most test seeds reach the generator through parametrize or variables, not literal `seed=` arguments, so a check on the source text would miss them (Codex adversarial review, finding 1). Instead, during the test run, every seed passed to the generator is compared with the calibration ranges in the registry from ticket 03. The calibration routines themselves, the feasibility gate's calibration step and ticket 07's routine, are marked as allowed to use those ranges. Everything else fails if it touches one. See `../spec.md`.

**Blocked by:** 03

**Status:** resolved

- [x] Every calibration seed range in use is registered in ticket 03's module: the 100-199 range that `THRESHOLD` was set from, and the feasibility gate's calibration and probe-calibration ranges. The registry's own disjointness check covers all registered ranges, replacing the feasibility-only version.
- [x] During `make check` and `make check-slow`, every seed passed to the generator outside an explicitly marked calibration context is checked against the calibration ranges. A hit fails that test, naming the seed and the range.
- [x] The way to mark a calibration context is explicit and easy to find in a diff, and CLAUDE.md lists it as a protected surface.
- [x] Proof: each of these planted cases turns the gate red with the guard's message: a parametrized test over a calibration seed, a seed computed into a variable that lands in a calibration range, and an evaluation step that draws its frames from the calibration set. The plants are not committed.
- [x] `make check` and `make check-slow` stay green on the current tests. If an existing test is already caught, that is a finding: record it under `## Comments` and stop for the owner. Do not re-seed it on your own.

**Guarantee and known limits (Codex's holes).** Guarantee: during `make check`, `make check-slow`, `make test-fast` and `uv run python tests/feasibility.py`, every seed that seeds `denoisifier.synthetic.generate`'s RNG is checked against the registered calibration ranges, in the main process and in `score_batch`'s workers; a calibration seed outside its `calibrating(...)` block, or a non-int seed, raises `SeedGuardError`. Known limits, not fixed:
1. A pool or subprocess started without `seed_guard.install_worker` runs unguarded. Today `score_batch` is the only pool; CLAUDE.md lists the initializer as protected, and T7 covers the script's own path.
2. Frames or scores produced inside a `calibrating(...)` block and reused later are not seen; the guard sees generation, not data flow. T5 checks the block encloses only the calibration call; reuse of its output can only be caught by review.
3. Frames built without `generate` (a direct `np.random.default_rng(...)`) are not seen.
4. Calibration plans are linked to the registry by name: `test_seed_sets_are_disjoint_and_unused` checks that a `feasibility.SEED_SETS` entry is in `CALIBRATION_SEEDS` only when its name contains "calibration". A calibration set under another name would not be required to be registered.
5. `measure_all` (and `measure`, `score_batch`) is unguarded when called from an entry point other than pytest (conftest install) or `feasibility.main()`: nothing installs the guard there. Ticket 07's driver must call `seed_guard.install()` itself or go through `main()`.
