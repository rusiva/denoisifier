- [ ] B1 break: the plan pins threads to 1 only in test-side pools (`tests/feasibility.py:202` `run_pool`, `tests/evaluate_regions.py:277`, `tests/calibrate_regions.py:565`). It misses the package's own pool: `calibration.calibrate_folder` runs `analyse` in a spawn `ProcessPoolExecutor(workers, ...)` (`src/denoisifier/calibration.py:317`), a public API. With A3's default, a user's `workers=8` run becomes 8 x 4 threads. → Plan change: the package pool also runs its workers at 1 thread, through an initializer that sets the knob or a `threads` argument passed into `_score_file`. This pool has no seed guard, so it is not a guarded surface. Add a fast test that a `workers>1` run produces the same scores as `workers=1`.
- [ ] B2 break: "Thread count: one module-level knob, read once" collides with the protected-number lockfile. `tests/protected_lock.py:3-8` records the *live value* of every module- and class-level name in `denoisifier` that holds a number. A module-level `_THREADS = min(4, os.cpu_count())` or an env read at import would be pinned to one machine's value, and the pin would depend on `DENOISIFIER_THREADS` in the environment. `make check` would then go red on another laptop, or whenever the variable is set. The plan names lockfile edits only for `tests/protected.py`. → Plan change:
  - Read the env var lazily inside a function, not at import.
  - The only module-level number is the cap (e.g. `_MAX_BANK_THREADS = 4`). It is a new lockfile entry, so it needs an approval; list it in section 4/5.
  - Spell out how invalid values (`0`, negative, non-integer) are handled: raise, or fall back to the default.
  - The project runs Python 3.11 (`.python-version`). There, `os.cpu_count()` ignores CPU affinity and cgroup limits, so cap with `len(os.sched_getaffinity(0))`. `os.process_cpu_count` only exists from 3.13.
  - Give `estimate_local_stripes` an internal `threads=` argument, so the threads-1-vs-4 fast test (section 3.2) can switch the count in one process. A count read once at import cannot be switched there.
